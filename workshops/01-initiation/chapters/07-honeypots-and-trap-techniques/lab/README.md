**Format:** Round 0 plus 4 rounds of attack and defense, then a debrief. See `../chapter_07_content.md`, section 7.5.

You play both sides on the Kestrel Outfitters store. Each round the defender turns on the next trap, and the attacker runs the script that walks into it. Then the attacker runs the script that walks around it. Every checkpoint measures two things: the bots a trap catches, and the real people it catches by mistake. The second number is the one honeypot tutorials leave out.

## Rules of engagement

- **Local only, enforced in code.** Every attack script and tool reaches the store through `tools/labclient.py` (via `tools/trapkit.py`), which asks `labnet.py` at the lab root for `DEMO_URL` and refuses anything that is not this machine (side-service URLs such as `REDIS_URL` too). The store's edge accepts the lab headers only from loopback. Playwright runs through `labclient.browser_context`, which also aborts any request that leaves localhost. Do not remove those checks.
- **Everything is synthetic.** Every source address is a documentation address (RFC 5737, RFC 3849) rented from `data/world.json` and sent in `X-Lab-Client-IP`; every account and password is generated by the scripts or seeded by `demo_site/seed.py`. The "decoy" `.env` holds a made-up canary password. No proxy, VPN or real credential is ever used.
- **Outbound network:** none during the rounds. Only setup needs the internet: installing packages and the Chromium that Playwright drives.
- Do not point these scripts, or anything you build from them, at a site you do not own.

## What is in the folder, and how this lab is built

This lab is **wire-it**: the trap modules ship as working skeletons with a `TODO (Round N)` where you do the round's work, and the finished versions are in `solutions/roundN/`. `python tools/checkpoint.py --round N --catch-up` installs rounds 1..N (keeping your files as `.bak`); `--restore` puts yours back.

Setup is covered once for the whole series in `onboarding/setup/PREWORK.md`. For this lab:

```bash
cd lab

pip install -r requirements.txt -r requirements-browser.txt      # one venv per chapter
python -m playwright install chromium                   # the Round 2 and Round 3b attackers

```

No Docker is needed (SQLite and an in-process Redis). With Docker, `docker compose up -d --wait` starts Redis 8.10 and PostgreSQL 18 as in the starter README. Port 5000 busy (macOS: the AirPlay Receiver)? `PORT=8099 python demo_site/app.py`, then `export DEMO_URL=http://127.0.0.1:8099` in the shell where you run attacks and tools.

You never restart the store between rounds: edits to `defenses/*.py` are picked up on the next request, and the checkpoint sets the level (`POST /lab/level`). To set it by hand: `curl -s -X POST localhost:5000/lab/level -H 'Content-Type: application/json' -d '{"level": 2}'`. Restart only after editing `demo_site/ext/`.

| Level | Adds | Module |
|---|---|---|
| 0 | Nothing. Requests are logged, nothing is trapped | – |
| 1 | The textbook honeypot: a field called `website` inside `<div style="display:none">` | `form_traps.py` |
| 2 | The honeypot hidden by a class in `traps.css` with a per-session opaque name, and a signed timing token | `form_traps.py` |
| 3 | A hidden trap link and its archive maze, a honey SKU, decoy endpoints, `robots.txt` lines | `crawl_traps.py` |
| 4 | Sanctions: what a client that already tripped a trap gets next (`TRAP_RESPONSE_MODE` × `TRAP_SANCTION_KEY`) | `responses.py` |

Each level includes every level below it. Levels 1 to 3 only **detect**: a trapped signup gets the same redirect to a plausible `/account` page as a real one and nothing is saved (a *fake success*), and a trapped crawl gets its page. Level 4 also **sanctions** the client for 15 minutes.

**Look around while you work:**

```bash
curl -s localhost:5000/lab/traps | python -m json.tool                    # how the store sees YOU: level, your address, any sanction, the honeypot's config
curl -s localhost:5000/robots.txt                                         # the base policy plus the lines this chapter adds at level 3+
curl -s 'localhost:5000/lab/decisions?actor=bot:r1&limit=5' | python -m json.tool    # the trap log: signals, outcome, extra.account / extra.review
python tools/scoreboard.py                                                # bots stopped next to shoppers hurt
```

Every response carries `X-Lab-Verdict`, `X-Lab-Score`, `X-Lab-Signals` and `Server-Timing`. They tell the attacker exactly which trap fired (`form_traps:honeypot_field`): never send them in production (`LAB_HEADERS=0`). The lab's shoppers read `X-Lab-Signals` to learn they were trapped even when the page looked fine; no bot script here does.

**Debug routes** (never gated): `/lab/traps`, `/lab/decisions`, `/lab/scoreboard`, `/whoami`, `POST /lab/reset`. They replace the old lab's `/trap-check`, `/trap-logs` and `/lab/summary`.

## How to measure a round

```bash
python tools/checkpoint.py --round N                 # level N: your defenses
python tools/checkpoint.py --round N --level N-1     # the same attacks one level down: the "before"
python tools/checkpoint.py --round N --catch-up      # install solutions/round1..N first
python tools/checkpoint.py --restore                 # put your own files back
```

The checkpoint sets the level, resets the store, runs every attack introduced so far while the 40 shoppers sign up (the `signup` scenario), and prints PASS/FAIL. A full round takes about 30 to 60 seconds; most of it is the two Playwright attackers and the shoppers reading forms like people.

What it reports:

- **Bot traffic**, from the server's side. A trapped signup gets a fake success, so a bot's own count is what it *believes*. The checkpoint replaces it with what the decision log says the store did: accounts really created, reviews really published. The attack's own JSON is shown next to it (`believed`, `deceived`).
- **Shoppers**, from `tools/personas_ch7.py`: a shopper is hurt if a trap or sanction signal touched anything they did, or if the store blocked them. The scoreboard (`python tools/scoreboard.py`) counts only people whose *last* request was stopped; a silently dropped signup does not show there. The persona table does.
- **Defender cost:** the scoreboard's `gate ms` column and `Server-Timing` (see the cost note below the results).

| Persona | Models | A trap hurts them if… |
|---|---|---|
| `home`, `consumer_vpn`, `private_relay`, `old_chrome`, `no_js` (28) | sighted people with a mouse | it is visible (none of ours are) |
| `screen_reader` (2) | keyboard and screen-reader users who fill whatever Tab lands on | the honeypot can take focus |
| `autofill` (1) | browser autofill and a password manager, filling in 1.2 to 1.6 s | the honeypot has a layout box and a name or label like `phone`, or the timing threshold is above 1.2 s |
| `search_crawler` (1) | a search engine that obeys `robots.txt` (RFC 9309) and reads raw HTML | a trap URL is not in `robots.txt` |
| `mobile_cgnat` (8) | customers on a mobile carrier. They sign up and post a review, and share the address the Round 4 bot rents | sanctions are keyed on IP |

The autofill and screen-reader personas are **models**. The shoppers are Python, not browsers, so `personas_ch7.py` reads the store's real `traps.css` and decides from it which fields have a layout box, which are off-screen and which the Tab key reaches. Real autofill heuristics differ by browser and version. In Round 2, also try the form in your own browser with its autofill and password manager on. `search_crawler` is counted as a person (`human:` in the scoreboard) so that trapping Googlebot shows up as a false positive.

**Fell behind?** `python tools/checkpoint.py --round N --catch-up` copies the reference files for rounds 1..N over yours (one `.bak` per file). The store reloads them by itself.

| Step | Do | Expected |

| 🛡️ Defend | Write the `TODO (Round 4)` in `defenses/responses.py`, wire `responses.CHECK` at `LADDER[4]`, set level 4 | – |

`round4_probe.py` wipes the store, runs the Round 4 bot, **then** a customer from the carrier address the bot shares, and prints what each of them lived. Order matters: the bot goes first so the sanction exists when the customer arrives.

| `TRAP_RESPONSE_MODE` / `TRAP_SANCTION_KEY` | What the bot concludes | The carrier customer |
|---|---|---|
| `block` / `ip` | `blocked` ×3: the 403 told it exactly which request failed | ❌ blocked with a 403 |
| `fake` / `ip` | `shadow-banned` ×3: the signup looked fine, then the login fails | ❌ signup silently dropped, can't log in |
| `quarantine` / `ip` | `success` ×3: login works, and it can see its own review | ❌ looks fine to them, but the account is quarantined and the review hidden. **The worst kind of false positive: nobody complains.** |
| `quarantine` / `session` | `success` ×3; reviews published: 0 | ✅ unaffected |

**Discuss:**

- How would the Round 4 bot detect the shadow ban? (Look for its review from a second, clean session.) What would you do next?
- The bot drops its cookie and comes back clean. Why is that acceptable here, and when isn't it?
- Why isn't tarpitting (`time.sleep(5)` before responding) one of the modes? Whose thread is sleeping?
- Run `python attacks/round4_verify_signup.py` at level 3. Why does the bot conclude `shadow-banned` there, with no sanction in place?

**Defender cost.** Median over 400 product-page requests through the full ladder, in-process Redis: the store itself `app` ≈ 9 ms; the whole gate (`gate`) 0.7 ms at level 0, 0.8 ms at level 3, 1.2 ms at level 4. Each trap check is about 0.01 ms (a path compare, or an HMAC on a signup POST). The sanction lookup (`responses`) is about 0.3 ms: one Redis GET per request, in-process here and a network round trip against the Docker Redis. The numbers under load in the scoreboard are higher because the store, Redis and 40 shoppers share one Python process.

Things to watch for:

- **Level 1 or 2 looks untrapped:** the check is not wired in `ladder.py`, or the store is on another level (`/lab/traps` shows it).
- **`too_fast` on a real person:** `MIN_FILL_SECONDS` is 1.0 s. The autofill shopper takes 1.2 to 1.6 s. If your own autofill-plus-generated-password signup gets trapped, that is a real finding. Discuss it; don't hide it.
- **The Round 4 numbers depend on order.** The checkpoint runs the bots and the shoppers at the same time, so with `block` / `ip` the carrier customers are only sometimes hurt. `tools/round4_probe.py` runs the bot first, every time.
- **`ext/` changes need a restart.** `demo_site/ext/traps.py` is not hot-reloaded; `defenses/*.py` and `policy.py` are.
- **Honey SKU and smoke tests:** the hidden product exists only while the store runs at level 3 or above, so `tools/smoke.py` (which counts 122 products) passes at level 0 and would count 123 at level 3.
- **`robots.txt` and Python:** the store's base policy starts with `Allow: /`. Python's `urllib.robotparser` applies the first matching rule and so ignores every later `Disallow`; RFC 9309 applies the longest match. `tools/trapkit.py` implements RFC 9309 for the crawler persona and the polite crawler. If you write your own crawler, test it against this file.

## Troubleshooting

| Problem | Fix |
|---|---|
