**Format:** five rounds of defend 🔵 and attack 🔴, one per attacker economy, then a debrief. See `workshops/03-advanced/chapters/04-specialized-attack-scenarios/chapter_04_content.md` (slides repo). **Style: wire-it.** Each defense ships as a stub in `defenses/` with a `TODO (Round N)`; the finished version is in `solutions/roundN/`. `--catch-up` installs rounds 1..N (the check and `ladder.py`), and `--restore` puts your files back.

The spine of the chapter: **an attack's economics force a signature it cannot hide, and the defense that works targets that signature, not a generic "is this a bot" score.** You play defender against five specialized attackers (a credential stuffer, a scalper, a scraper, a fake-account farm, a click fraudster). Each round you finish one check, run the attackers that beat the previous step, and read the scoreboard: what the attacker got, next to the real shoppers the defense hurt.

This lab runs the **whole** Kestrel store; it is not a slice. Each scenario happens on a route the store already has (`/api/login`, the drops, the catalogue, `/register`), except the ad tracker, which `demo_site/ext/economies.py` adds.

## Rules of engagement

- **Local only, enforced in code.** Every attack script and tool imports `tools/labclient.py`, which asks `labnet.py` at the lab root for `DEMO_URL` and refuses anything that is not this machine (side-service URLs such as `REDIS_URL` too). The store's edge accepts the lab headers only from loopback. Do not remove that check.
- **Everything is synthetic.** The accounts are the starter's `user000..299@example.test`. The "breach" the stuffer replays is generated by `attacks/_common.py: combo_list()` from the seed's own weak users (`user000` to `user029`, who reuse one of the 30 passwords in `data/wordlists/passwords_top.txt`) hidden among invented `strangerNNNNNN@example.test` addresses. The breach corpus is that same wordlist, hashed and bucketed the way the Have I Been Pwned range API answers. The disposable-domain list, the ad campaign and every inbox are invented. Nothing is, or was derived from, real credentials.
- Source addresses are rented from `data/world.json` (documentation ranges: `cloud_vm` for the datacenter attackers, `residential_proxy_net` for the ones that pay for a fleet) and sent in `X-Lab-Client-IP`, which the store's edge trusts only from loopback. No proxy, no real address, no third-party site.
- **Outbound network:** none during the rounds. The one opt-in exception is `HIBP_LIVE=1`: it makes the Round 1 breach lookup (`defenses/breachcorpus.py`) ask the real Pwned Passwords range API (`https://api.pwnedpasswords.com/range/<5 hex>`) instead of the offline mirror. It sends only the first five hex characters of a SHA-1 hash, it is **off by default**, and the lab's results (and the numbers below) are for the offline corpus. Only setup needs the internet: installing packages and container images.
- Do not point these scripts, or anything you build from them, at a site you do not own.

```
lab/
  demo_site/ext/economies.py   the surfaces: the facts (ctx.attrs["catalog" | "drop" | "signup"]) the defenses decide on,
                               the honeypot SKUs p121/p122 and the invisible link to them (level 3+), the per-session
                               canary, and the ad tracker (POST /api/ads/impression | click, GET /api/ads/report)
  demo_site/ext/step_up.py     the login's second phase (action:login_result) and the emailed-code "otp" challenge
  defenses/                    breached_passwords · scalping_funnel · scrape_defense · account_cluster · ivt_scoring
                               (your five stubs) · ladder.py (yours) · generic_layers · breachcorpus · netinfo (finished)
  solutions/round1..5/defenses/ the finished check and the ladder as it stands after each round
  attacks/                     round1_stuffer · round2_scalper (--skip-view, --patient) · round3_scraper (--skip-hidden)
                               round4_account_farm (--clean-emails) · round5_click_fraud (--sivt) · _common.py
  tools/                       personas_ch4.py (the shoppers' scenarios) · checkpoint.py (ROUNDS and thresholds)
  data/disposable_domains.txt  the synthetic blocklist
```

The rest of the store (catalogue, cart, checkout, the simulated edge, the decision log) is the W3 starter, unchanged. Its contract is `workshops/STORE_CONTRACT.md`.

**Round 0.** The W3 starter's baseline is empty, so this lab adds its own: `defenses/generic_layers.py`, a per-IP rate limit (500 requests per address per 10 seconds), wired at `LADDER[0]` so it runs at every level before any scenario check. Every attacker rents a pool of addresses and rotates per request, so the limit never trips: it counts requests, and the five economies are not about requests. (It is a plain counter, not the starter's Lua token bucket: on the in-process Redis a Lua script serializes under the attackers' 16 threads and would bury the gate cost of the checks you write. The file explains the trade-off.)

**Two facts the store gives a check.** The starter runs a check before the route, which is too early for "the password was right" (Round 1) and too general for "this is a drop purchase" (Round 2). `demo_site/ext/economies.py` fills `ctx.attrs` on the request, and `demo_site/ext/step_up.py` adds `action:login_result`, a phase that runs after the login with the outcome in `ctx.attrs["login"]`. A check that asks for the `otp` challenge takes the session back: the store emails a six-digit code (read it in `/lab/mailbox/<email>`) and the session exists only after `POST /api/challenge/verify`. A failed login is never rewritten; it keeps its 401.

## Setup

Work through `PREWORK.md` first. This lab needs nothing beyond the starter's packages:

```bash
cd lab
python3.12 -m venv .venv && . .venv/bin/activate        # one venv per chapter, see the root README
pip install -r requirements.txt
python tools/doctor.py
python demo_site/app.py                                  # terminal 1: the store, on :5000 (seeds itself)
python tools/verify.py --smoke                           # terminal 2: the contract, as a test (optional)
```

Docker is optional: the default is SQLite plus an in-process Redis. To run the production-shaped stack (Redis 8.10 and PostgreSQL 18):

```bash
docker compose up -d --wait
REDIS_URL=redis://127.0.0.1:6379/0 DATABASE_URL=postgresql+psycopg://workshop:workshop@127.0.0.1:5432/shop python demo_site/app.py
docker compose down -v                                   # when you are done
```

Round N runs at `DEFENSE_LEVEL` N and each level includes every level below it; the checkpoint changes the level live (`POST /lab/level`), so the store never restarts between rounds. You finish a stub, wire it in `defenses/ladder.py`, save (the store reloads `defenses/` on the next request), and measure:

```bash
python tools/checkpoint.py --round 1                    # your code
python tools/checkpoint.py --round 1 --catch-up         # the reference solutions for rounds 1..1 (your files kept as .bak)
python tools/checkpoint.py --restore                    # put your own files back
python tools/checkpoint.py --round 1 --level 0          # the round's attackers against the PREVIOUS level (the "before")
python tools/scoreboard.py                              # the last run, per actor
```

(`python tools/verify.py --round N` does the same against a store it starts in-process on a free port, which is how the numbers below were produced.)

| Level | Round | Adds | Module you finish |
|---|---|---|---|
| 0 | – | A per-IP rate limit that every attacker rotates past | – (`generic_layers.py`, finished) |
| 1 | 1 | A correct-but-breached password needs an emailed code | `defenses/breached_passwords.py` |
| 2 | 2 | Funnel integrity and one unit per device on the drop | `defenses/scalping_funnel.py` |
| 3 | 3 | Honeypot SKUs and catalogue coverage | `defenses/scrape_defense.py` |
| 4 | 4 | Disposable domains, egress velocity and device clusters at sign-up | `defenses/account_cluster.py` |
| 5 | 5 | GIVT hard filters and the SIVT engagement funnel on ad clicks | `defenses/ivt_scoring.py` |

Each check scores on the starter's 0 to 100 scale (`defenses/policy.py`): 40 and up is a `challenge`, 75 and up a `block`. Only the `otp` challenge has a solver (the lab mailbox); any other challenge band score is **enforced as a block**, and the scoreboard shows it that way. Lab routes (loopback only, never scored): `/whoami`, `/lab/status`, `/lab/decisions`, `/lab/scoreboard`, `/lab/mailbox/<email>`.

> Every response carries `X-Lab-Verdict`, `X-Lab-Score` and `X-Lab-Signals` (for example `scrape:honeypot`). That is for teaching only. In production, never tell a client which rule caught it.

## The people

Every round runs the starter's 40 shoppers (`tools/personas_ch4.py` gives them a scenario that mirrors the round's attack surface), next to the attackers:

| Persona | n | Why they are here | Where they pay |
|---|---|---|---|
| `home` | 24 | the easy majority, own address, Chrome, Firefox, Safari | nowhere: they must never be stopped |
| `mobile_cgnat` | 8 | six phones share one carrier address, two share another | Round 4: the egress cap asks three of them for a code |
| `consumer_vpn` | 3 | commercial VPN addresses (shared, datacenter-like) | Round 5: a 25-point observe signal, never a block |
| `private_relay` | 2 | Apple-style privacy relay: real people on hosting ranges | nowhere (0 points: paying Safari customers) |
| `old_chrome` | 1 | Chrome 138; reuses a top-30 password (user 020); **compares 18 products** | Round 1: an emailed code · Round 3: closest to the ceiling |
| `autofill` | 1 | fills forms in 1.2 to 1.6 s; reuses a top-30 password (user 021); clicks ads fast | Round 1: an emailed code · Round 2 and 5: closest to the floors |
| `no_js` | 1 | Firefox with privacy settings: the `Referer` header is stripped | Round 5: a 30-point observe signal |

**Hurt** means a person ended stopped. **Stepped up** means they were asked for a code and entered it: friction, not harm. The checkpoint also prints the gate time of the shoppers' requests (the defender's cost) from the decision log.

## Round 1: 🔵 breached-password step-up ⚔️ 🔴 distributed stuffer (`DEFENSE_LEVEL=1`)

| Step | Do | Expected |
|---|---|---|
| 🔴 Attack | `python attacks/round1_stuffer.py` (1000 pairs, each from the next of 384 residential-proxy addresses) | 30 accounts taken over: the generic limit never trips |
| 🔵 Defend | Finish `defenses/breached_passwords.py` (a correct password that is in `breachcorpus.pwned_count` earns the `otp` challenge), wire `1: [breached_passwords.CHECK]` in `defenses/ladder.py` | – |
| ✅ Checkpoint | `python tools/checkpoint.py --round 1` | stuffer 0 (30 right passwords met a code) · **2 shoppers stepped up** |

**False-positive check:** the two shoppers whose real password is in the corpus (users 020 and 021) now enter a code. They get in; count it as friction, and ask what prompt rate would make you refuse to ship it. This is the stuffing economy only: W2 Ch6 is the full arms race (sprays, clean lists, infostealers, session replay).

## Round 2: 🔵 funnel integrity ⚔️ 🔴 scalper (`DEFENSE_LEVEL=2`)

| Step | Do | Expected |
|---|---|---|
| 🔴 Attack | `python attacks/round2_scalper.py` (80 attempts: view the drop, buy in the same breath, four device cookies) | the bot sweeps the drop (48 to 50 of 50) and the 40 shoppers find it gone |
| 🔵 Defend | Finish `defenses/scalping_funnel.py` (no view → block, one attempt per device → block, view-to-buy under 1.0 s → challenge), wire `2: [scalping_funnel.CHECK]` | – |
| 🔴 Re-attack | `python attacks/round2_scalper.py --skip-view` (POST the buy without viewing the drop) · `--patient` (wait 1.1 s, four device cookies) | skip-view **0** · patient **4**, one pair per device cookie |
| ✅ Checkpoint | `python tools/checkpoint.py --round 2` | all three attackers within bounds · bots bought at most 4 · **40 of 40 shoppers buy** |

**Discuss:** the patient bot is stopped by the device cap alone, and the cap is only as good as the identity it counts: `did` is attacker-chosen, so a fresh cookie per attempt walks past it. Say what you would count instead (account age, a fingerprint from W2 Ch2, the payment card).

## Round 3: 🔵 honeypot SKUs and coverage ⚔️ 🔴 scraper (`DEFENSE_LEVEL=3`)

| Step | Do | Expected |
|---|---|---|
| 🔴 Attack | `python attacks/round3_scraper.py` (reads the 5 listing pages, follows every product link, a new residential address per request) | 120 of 120 product pages harvested |
| 🔵 Defend | Finish `defenses/scrape_defense.py` (honeypot hit → flag the session and block, distinct items per session over 25 → block), wire `3: [scrape_defense.CHECK]` | – |
| 🔴 Re-attack | `python attacks/round3_scraper.py --skip-hidden` (skips links a person cannot see) | **0** for the default crawler (it follows the invisible link to `p121` first) · **20** for the one that skips it, cut off by coverage at the 26th item |
| ✅ Checkpoint | `python tools/checkpoint.py --round 3` | crawler 0 · trap-aware 20 · nobody hurt (the researcher views 18 products) |

The honeypot products and the invisible link exist only from level 3 (so `--level 2` shows the "before"), and `robots.txt` tells crawlers to skip them. The scraper prints the per-session canary it found in the HTML; the same token is in every page you load (`<span hidden data-canary=…>`). If it ever turns up in a competitor's catalogue you know which session scraped you.

**False-positive check:** a hard ceiling lands on your most engaged customers; the researcher is 7 items under it. What would you set it to from a real distribution? Rotating sessions below the ceiling beats it, and only the honeypot or an aggregate per network sees that.

## Round 4: 🔵 cluster signals ⚔️ 🔴 account farm (`DEFENSE_LEVEL=4`)

| Step | Do | Expected |
|---|---|---|
| 🔴 Attack | `python attacks/round4_account_farm.py` (20 registrations from one hosting address and three browser profiles, disposable inboxes) | 20 accounts created |
| 🔵 Defend | Finish `defenses/account_cluster.py` (disposable domain 100, egress above 3 in 5 minutes 45, device above 2 in 5 minutes 45; they add up), wire `4: [account_cluster.CHECK]` | – |
| 🔴 Re-attack | `python attacks/round4_account_farm.py --clean-emails` (real-looking domains) | **3** accounts, then the cluster bites: the blocklist was evaded, the velocity was not |
| ✅ Checkpoint | `python tools/checkpoint.py --round 4` | farm 0 · clean-emails 3 · **3 phones stepped up** (the 4th to 6th sign-ups from the shared carrier address) |

**False-positive check:** carrier-grade NAT, a campus, an office. Three real first-time customers are asked for an inbox because they share an address with three others. Is three acceptable for the farm? How would you drive it to zero without blocking a campus?

## Round 5: 🔵 invalid-traffic scoring ⚔️ 🔴 click fraud (`DEFENSE_LEVEL=5`)

| Step | Do | Expected |
|---|---|---|
| 🔴 Attack | `python attacks/round5_click_fraud.py` (GIVT: 60 clicks from hosting addresses, library User-Agent, no Referer, no impression) | 60 of 60 clicks billed |
| 🔴 Attack | `python attacks/round5_click_fraud.py --sivt` (six residential-proxy browser profiles: Referer, impression first, then instant clicks) | 60 of 60 clicks billed |
| 🔵 Defend | Finish `defenses/ivt_scoring.py` (GIVT: datacenter, bad User-Agent, no Referer; SIVT: no impression, dwell under 300 ms, over 8 clicks a minute), wire `5: [ivt_scoring.CHECK]` | – |
| ✅ Checkpoint | `python tools/checkpoint.py --round 5` | givt 0 (60 filtered under `givt_*`) · sivt 0 (60 filtered under `sivt_*`) · nobody hurt |

The residential-proxy fleet is invisible to every address feed (`netinfo` calls it residential, as production does), which is why the engagement funnel has to carry it. `GET /api/ads/report` is the advertiser's number: billed clicks.

**False-positive check:** the VPN users (25 points) and the no-Referer Firefox (30) are *observed*, not discarded, and still serve the click. A fast reader clicks in 0.4 s; the floor is 0.3 s.

## Wrap-up: the cross-scenario debrief

`python tools/checkpoint.py --all --markdown` prints every round's scoreboard. The arc is the point: each defense targets the thing the attack must do to profit (use a leaked password, buy faster than a person, cover the catalogue, share infrastructure, skip engagement), each is cheap for the defender to measure, and each lands on a nameable group of real people (password reusers, fast humans, researchers, shared-address users, privacy settings). No single signal is sufficient.

## Expected results (self-check)

Generated from `python tools/verify.py --all --catch-up --markdown` (against your own store: `python tools/checkpoint.py --all --markdown`) on 2026-10-14 on Linux x86_64 (WSL2) with Python 3.12.15, Flask 3.1.3, Flask-SQLAlchemy 3.1.1, SQLAlchemy 2.1.4, redis 8.1.0, fakeredis 2.39.0, requests 2.34.2, SQLite and the in-process Redis, `HIBP_LIVE` off. Every round passed with the reference solutions installed, twice in a row with the same figures; every `--level N-1` "before" run reported the round's attacker getting through. The Docker path (Redis 8.10, PostgreSQL 18) passed the smoke test and all five rounds.

| Round | Level | Attackers run | Got through (before → after) | Shoppers stepped up | Gate per shopper request, median / p95 |
|---|---|---|---|---|---|
| 1 | 1 | stuffer | 30 takeovers → **0** (30 right passwords met a code) | **2** (users 020, 021) | 2.4 / 11.2 ms |
| 2 | 2 | scalper, skip-view, patient | pairs: scalper 48 to 50 → **0**; skip-view 50 → **0**; patient 50 → **4** (one per device cookie) | 0 · **40 of 40** buy (before: 0 to 2) | 3.1 / 6.0 ms |
| 3 | 3 | crawler, trap-aware | pages: crawler 120 → **0** (honeypot); trap-aware 120 → **20** (cut off at the 26th item) | 0 · researcher untouched | 2.7 / 5.1 ms |
| 4 | 4 | farm, clean-emails | accounts: farm 20 → **0**; clean-emails 20 → **3** | **3** (carrier-NAT phones) | 4.1 / 5.5 ms |
| 5 | 5 | givt, sivt | billed clicks: givt 60 → **0**; sivt 60 → **0** (60 filtered under `sivt_*`) | 0 · nobody hurt | 3.0 / 5.8 ms |

Shoppers hurt (ended stopped): **0 of 40** in every round. The "before" scalper columns depend on the race for the 50 units: the machine-speed bot is the first to run, so the later two variants find the drop gone (`python attacks/round2_scalper.py --skip-view` alone, after `POST /lab/reset`, wins 50). With the Docker stack the gate time is higher (about 65 ms median in Round 1 under 16 stuffing threads, 9 to 11 ms in the others) because every check makes Redis round trips over TCP; the checkpoint allows 250 ms there instead of 20 ms.

## Troubleshooting

| Problem | Fix |
|---|---|
| Port 5000 taken (macOS AirPlay Receiver) | `PORT=5050 python demo_site/app.py`, then `export DEMO_URL=http://127.0.0.1:5050` in the shells that run tools |
| A round says `stuffer: got 30, expected 0-0` (or any attacker above its bound) | Your stub is not finished, or not wired in `defenses/ladder.py`. Finish the `TODO`, or `python tools/checkpoint.py --round N --catch-up` |
| Round 3 shows no `scrape:honeypot` | The honeypot SKUs and the hidden link exist only at level 3 and above; the checkpoint sets the level itself. If you changed it by hand, run the checkpoint again |
| Round 4 shows 0 stepped up | `DEFENSE_LEVEL` is below 4, or `IP_CAP` in your stub is 6 or more. The six carrier-NAT phones need a cap under 6 to meet it |
| `challenge_unavailable` for a shopper | A challenge band score with no solver is enforced as a block. Only `otp` has one; for any other check return a block-band score or `Verdict("challenge", challenge="otp", ...)` |
| Every login from your browser is refused | You are one address among the shoppers; `POST /lab/reset` clears the counters |
| Numbers look stale between rounds | The checkpoint resets the store (`POST /lab/reset`); if you ran an attack by hand, run the checkpoint to reset first |
| `ModuleNotFoundError: demo_site` | Run scripts from `lab/` (`python attacks/...`), not from inside `attacks/` |
| Want a clean slate | Stop the store, delete `instance/`, start it again |
| Port 5432 or 6379 taken (another lab's containers) | `docker compose ls`, then `docker compose -p <name> down` |
