**Format:** five rounds (0 to 4) of defend 🔵 and attack 🔴, then a debrief. See `../chapter_03_content.md`, §3.6. **Style: pre-written.** Every detector ships complete; you read it, switch `DEFENSE_LEVEL`, and watch what the next attacker does to it. `solutions/roundN/defenses/ladder.py` is the ladder as it stands after Round N, and `--catch-up` installs it (your own `ladder.py` is kept as `.bak`; `--restore` puts it back). Catching up also just means running the round at its level, which the checkpoint does for you.

The spine of the chapter: **a streaming verdict stops what comes after it, never what came before.** Every request becomes one event on a Redis Stream. A consumer scores the stream in milliseconds and raises a flag; the gate refuses the next request that flag names. You measure the price of that latency in the attacker's column (how many attempts were served before the first refusal) and in the shoppers' column (how many people the flag hurt), and you watch the consumer's backlog, because a detector that falls behind the traffic reopens the gap it came to close.

## Rules of engagement

- **Local only, enforced in code.** Every attack script and tool reaches the store through `tools/labclient.py`, which asks `labnet.py` at the lab root for `DEMO_URL` and refuses anything that is not this machine (side-service URLs such as `REDIS_URL` too). The store's edge accepts the lab headers only from loopback. Do not remove that check.
- **Everything is synthetic.** The accounts are the starter's `user000..299@example.test`; the "stolen credentials" are wrong guesses generated by `attacks/_common.py`. Source addresses are rented from `data/world.json` (documentation ranges: `cloud_vm` for the datacenter attackers, `residential_proxy` and `residential_proxy_net` for the ones that pay for a fleet) and sent in `X-Lab-Client-IP`. No proxy, no real address, no third-party site.
- **Outbound network:** none during the rounds. Only setup needs the internet: installing packages and container images.
- Do not point these scripts, or anything you build from them, at a site you do not own.

## How it fits together

```
request -> gate (ladder: the gate halves) -> route -> on_response: XADD event -> lab:stream:events
                                                                                      |
              consumer thread (XREADGROUP, group "detectors") -- scores with the detect() of every check
              the ladder enables at the current level -- writes a flag  lab:stream:flag:<detector>:<kind>:<value>
                                                                                      |
next request from that IP / session / account -> the detector's CHECK does one MGET -> block
```

```
lab/
  demo_site/ext/stream.py    the event log (XADD after the response), the consumer thread, and the lab routes:
                             GET /lab/stream/status (backlog, events/s, the detectors live now), GET /lab/stream/verdicts,
                             POST /lab/stream/consumer {"delay_ms", "consumers"} (the backpressure knob)
  defenses/
    streamlog.py             the stream, the consumer group, the flags, the lab clock (read the docstring)
    features.py              per-session state (Welford) and the sketches (Count-Min, HyperLogLog, Top-K)
    window_rate.py           Round 1: sliding-window rate per (IP, endpoint). flags the IP
    heavy_hitters.py         Round 2: velocity + distinct failing IPs, gated on the stuffing shape. flags the session
    regularity.py            Round 3: timing regularity (Welford CV). flags the session
    cross_key.py             Round 3: distinct IPs per account (HyperLogLog). flags the account
    composite.py             Round 4: weighted composite with a global campaign term. flags the session
    consumer.py              the scorer: reads a batch, runs the enabled detectors, acknowledges
    ladder.py                the levels (yours: the starter's wiring file)
  attacks/                   _common.py (the schedule runner) · round0_recon · round1_microburst · round2_ip_rotation
                             round3_low_and_slow · round4_jittered_browser
  tools/                     personas_ch3.py (the shoppers) · checkpoint.py (ROUNDS and thresholds) · lag.py
  solutions/round1..4/defenses/ladder.py
```

A detector has two halves. `detect()` runs in the consumer, on the stream, and may be as expensive as it likes (it is allowed to be a few milliseconds behind). `CHECK` runs in the gate on the next request and does a single `MGET`; it is what makes a verdict an action. The ladder lists the checks, and the consumer scores with the `detect()` of every check the ladder enables at the current level, so `/lab/status` always shows what is live and level 0 scores nothing.

**The lab clock.** The windows are shorter than production so that a round fits in under a minute: rate 10 s (production 60), failed-login velocity 60 s (600), distinct IPs per account 120 s (3600), a flag lasts 120 s. The sketch windows are tumbling and aligned to the first event after a reset, so no round straddles a window boundary by accident. A real deployment has no such luck; the content doc explains why production uses sliding or hopping windows.

**No assets, no ground truth.** The shoppers and the bots are Python, not browsers: they do not fetch `/static/` (which the gate skips anyway). "Looks human" is therefore page views (`/`, `/products`, `/product/<sku>`), and the stuffing shape is "fails logins, views no page, never buys". The event never carries the ground-truth actor; the scoreboard joins on it from the decision log.

## Setup

Work through `onboarding/setup/PREWORK.md` first. This lab needs nothing beyond the starter's packages (plus fakeredis's `probabilistic` extra):

```bash
cd lab
python3.12 -m venv .venv && . .venv/bin/activate        # one venv per chapter, see the root README
pip install -r requirements.txt
python tools/doctor.py
python demo_site/app.py                                  # terminal 1: the store, on :5000 (the consumer runs inside it)
python tools/verify.py --smoke                           # optional: the contract, as a test (starts its own store)
```

The default store is SQLite plus an in-process Redis (`memory://`, fakeredis 2.39), which implements Redis Streams (`XADD`, `XGROUP`, `XREADGROUP`, `XACK`, `XINFO`, `XPENDING`) and the probabilistic commands (`CMS.*`, `TOPK.*`, `PFADD`), so **no Docker is required**. The consumer is a thread of the store process because that is the only client that shares the in-process Redis; against a real Redis it could run anywhere.

To run the production-shaped stack (Redis 8.10 and PostgreSQL 18):

```bash
docker compose up -d --wait
export REDIS_URL=redis://127.0.0.1:6379/0
export DATABASE_URL=postgresql+psycopg://workshop:workshop@127.0.0.1:5432/shop
python demo_site/app.py
```

Redis 8 is required on the real-server path, because this chapter uses the Count-Min, Top-K and HyperLogLog structures that Redis 8 ships in core. Bring it down with `docker compose down -v`.

## How to measure a round

```bash
python tools/checkpoint.py --round 1        # level 1: the attacker, and the 40 shoppers next to it
python tools/checkpoint.py --round 3 --level 2   # the same attacker against Round 2's detectors (the "before")
python tools/checkpoint.py --all --markdown      # every round (the table below)
```

A round passes when the attacker's numbers are inside the expected ranges **and no shopper was stopped** and the median gate cost stays under 20 ms (250 ms on a real Redis, where every check is a round trip). Each run prints, besides the scoreboard:

```text
the stream: 557 events · consumer 134 events/s · backlog now 0 · 1 flags from window_rate
  a flag lands 6 ms (median), 6 ms (p95) after the event that tripped it

the attacker (microburst)
  served 21/300 attempts · 1/1 sessions met a refusal
  first refusal 0.71 s into a 10.0 s campaign, after 21 attempts were served (a session-end scorer waits ~10.0 s)
```

`served` is login attempts the store answered (a 401) rather than refused (a 403); `caught` is sessions that met at least one refusal; `first refusal` and `attempts served before it` are the detection latency; the line in brackets is what a session-end scorer would have waited.

## Round 0: the latency gap

- **Attack step:** `python tools/checkpoint.py --round 0`. The micro-burst (300 failed logins in ten seconds from one datacenter IP) runs at level 0. The store writes every request to the stream, but nothing reads it.
- **Observe:** 300 of 300 served, no refusal. A scorer that waits for the session to end waits ~10 s; one that runs every five minutes waits five. The `the stream` line shows the log filling and the consumer reading and acknowledging without scoring anything.
- **Checkpoint:** `python tools/checkpoint.py --round 0`.

## Round 1: 🔴 micro-burst ⚔️ 🔵 sliding-window detector (`DEFENSE_LEVEL=1`)

- **Defense step:** read `defenses/window_rate.py`: a sorted set per (IP, endpoint), trimmed to the window on every event; more than 20 logins in the window flags the IP.
- **Observe:** 21 of 300 served, the first refusal 0.71 s in, instead of ten seconds. The 21 are the price of the threshold plus the few milliseconds the flag takes to land.
- **False-positive check:** the 40 shoppers, including eight phones sharing two carrier-NAT addresses, stay clear. Set the login threshold in `window_rate.py` to 2 and rerun: three of the six phones behind one carrier address are stopped (the shoppers' column), and the attacker is stopped after 3 logins. Restore the 20 afterwards.
- **Checkpoint:** `python tools/checkpoint.py --round 1`.

## Round 2: 🔴 IP rotation ⚔️ 🔵 heavy hitters + distinct counts (`DEFENSE_LEVEL=2`)

- **Attack step:** `attacks/round2_ip_rotation.py`: the same campaign over 40 datacenter addresses, four tries each, each address its own session. No address is busy.
- **Defense step:** `defenses/heavy_hitters.py`: a Count-Min sketch of failed logins per endpoint and a HyperLogLog of distinct failing IPs say "a campaign is live"; the session shape (3+ failures, no page view, no purchase) says "this session is part of it".
- **Observe:** level 1 serves all 160; level 2 serves 120 (three tries of every session) and every one of the 40 sessions meets a refusal. The fourth try is the one stopped: the shape needs three failures to exist.
- **False-positive check:** people who fail a login once (the autofill shopper does) or browse first never match the shape.
- **Checkpoint:** `python tools/checkpoint.py --round 2`.

## Round 3: 🔴 low and slow ⚔️ 🔵 regularity + distinct-IP fan-out (`DEFENSE_LEVEL=3`)

- **Attack step:** `attacks/round3_low_and_slow.py`: five accounts attacked from 300 residential-proxy addresses, one try per address (a third retry once), over 23 seconds.
- **Defense step:** `defenses/cross_key.py` (distinct IPs per account, flagging the *account*) and `defenses/regularity.py` (Welford CV; silent here by design, because one request per IP leaves no gaps to measure).
- **Observe:** level 2 serves all 386; level 3 serves 116. The first ~20 distinct addresses of each account get through before the fan-out crosses the threshold: that is the latency of distinct counting, and 215 of 300 sessions meet a refusal after it.
- **False-positive check:** each shopper logs into their own account from one address (fan-out 1). The cost to name: once an account is flagged, its real owner is refused too (in production you step them up).
- **Checkpoint:** `python tools/checkpoint.py --round 3`.

## Round 4: 🔴 jittered browsers ⚔️ 🔵 composite + lag honesty (`DEFENSE_LEVEL=4`)

- **Attack step:** `attacks/round4_jittered_browser.py`: 80 browser-like sessions, own address each, page views, jittered timing, rotated accounts; most try four credentials, a patient quarter tries one.
- **Defense step:** `defenses/composite.py`: a weighted sum whose largest term is a *campaign* term (this session failed twice, and the global failed-login velocity or IP fan-out is far past normal).
- **Observe:** level 3 serves all 269; level 4 serves 159, and 57 of 80 sessions meet a refusal. The patient quarter never fails twice and stays under the line: the honest residual, and the hand-off to W3 Ch10.
- **Lag step (observe, no pass/fail):** run the micro-burst against a slow consumer, then against more of them:
  ```bash
  python tools/lag.py                          # 100 ms of work per event: capacity 10 events/s against 30 arriving
  python tools/lag.py --delay-ms 0             # the fast consumer
  python tools/lag.py --delay-ms 100 --consumers 6
  ```
  Reference capture of the first command on the machine below (read the shape, not the digits):
  ```text
   t(s)  arrived  handled  backlog
    1.0       15        4       11
    2.1       45       14       31
    5.1      138       43       95
   10.8      300       97      203
   16.4      300      150      150
   21.5      300      199      101
   32.2      300      300        0
  the first refusal came 2.24 s in, after 67 logins were served; 67/300 were served in all.
  peak backlog 203 events; the consumer was caught up 32.2 s after the burst began.
  ```
  With no added work the first refusal comes at 0.71 s after 21 logins and the backlog peaks at 1; six consumers at 100 ms keep up (peak backlog 4, 24 logins served). The ratio of arrival rate to capacity decides everything.
- **Checkpoint:** `python tools/checkpoint.py --round 4`.

## Wrap-up: the scoreboard

Every round reported **0 shoppers hurt of 40** next to the attacker's column. Walk it: which detector caught which shape, how many attempts each let through before it landed (21, 120, 116, 159), what the flag cost the person it named (an IP behind a NAT, a session, an account's owner), and why W3 Ch10 owns the monitoring, drift and retraining that keep these thresholds honest over time.

## Expected results (self-check)

## Troubleshooting

| Problem | Fix |
|---|---|
| `Store not reachable` | Start it: `python demo_site/app.py`, or use `python tools/verify.py --round N`, which starts its own on a free port. |
| `Cannot connect` to Redis, or CMS/TopK errors | With `REDIS_URL=redis://...` you need Redis 8 (the compose file pins `8.10.2-alpine`); on `memory://` install `fakeredis[lua,probabilistic]` from `requirements.txt`. |
| A round fails with "backlog" or the served counts drift | The consumer shares the machine with the attackers and shoppers. Close CPU-heavy programs and rerun; ranges allow a few attempts of slack, not a slow machine. |
| Flags from the last round block this one | `POST /lab/reset` flushes `lab:*` (flags, sketches, the stream); the checkpoint does it for you. A flag lasts 120 s on its own. |
| Port 5000 in use | `PORT=8099 python demo_site/app.py` and `export DEMO_URL=http://127.0.0.1:8099`. |

## Bonus challenges

- Rotate the sketch buckets by a sliding scheme instead of the epoch-aligned tumbling windows and make a campaign straddle a boundary on purpose; compare the Count-Min estimate with an exact counter to see the over-count.
- Run `python tools/lag.py --delay-ms 100 --consumers 3` and find the smallest group that keeps up with 30 events per second.

- Make the `composite` challenge band real: register a challenge type (the `challenge` verdict is enforced as a block today) and see which shoppers are asked.

## Why these tools

One primary language, Python 3.12+, because the whole series is Flask + Redis and Redis Streams is the native event log: `XADD` to emit, consumer groups to read, the probabilistic commands in the same server. No secondary language, no broker, no per-detector worker. Kafka, Faust, Bytewax and Flink are the scale-out answer discussed in §3.7; Redpanda is capable but source-available under the BSL (not OSI-approved), so it stays conceptual.
