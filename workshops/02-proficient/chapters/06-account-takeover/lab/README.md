**Format:** Round 0 plus 4 rounds of defend 🛡️ and attack 🗡️, then a debrief. See `workshops/02-proficient/chapters/06-account-takeover/chapter_06_content.md` (slides repo), §6.6. **Style: wire-it.** Each defense ships as a stub in `defenses/` with a `TODO (Round N)`; the finished version is in `solutions/roundN/`. `--catch-up` installs rounds 1..N (the checks and `ladder.py`), and `--restore` puts your files back.

You play both sides of the store's sign-in. The attacker holds a synthetic combo list, then infostealer output; you add one defense per round, run the attacker that beats it, and read the scoreboard: accounts taken over next to the real people the defense hurt.

## Rules of engagement

- **Local only, enforced in code.** Every attack script and tool imports `tools/labclient.py`, which asks `labnet.py` at the lab root for `DEMO_URL` and refuses anything that is not this machine (side-service URLs such as `REDIS_URL` too). Do not remove that check.
- **Everything is synthetic.** The 300 accounts are the starter's `user000..299@example.test`. The "breach" the stuffers replay is generated by `attacks/_common.py: combo_list()` from the seed's own weak users (`user000` to `user029`, who reuse one of the 30 passwords in `data/wordlists/passwords_top.txt`) hidden among invented `strangerNNNNNN@example.test` addresses. The breach corpus is that same wordlist, hashed and bucketed the way the Have I Been Pwned range API answers. The "stolen" cookies come from logging the lab's own users in. Nothing is, or was derived from, real credentials.
- Source addresses are rented from `data/world.json` (documentation ranges) and sent in `X-Lab-Client-IP`, which the store's edge trusts only from loopback. No proxy, no real address, no third-party site.
- **Outbound network:** none during the rounds, and nothing in this lab calls the real Have I Been Pwned service. Only setup needs the internet: installing packages and container images.
- Do not point these scripts, or anything you build from them, at a site you do not own.

```
lab/
  demo_site/ext/ato.py          the feature: the login's second phase (action:login_result), the emailed-code "otp"
                                challenge, the "reauth" challenge, POST /api/account/recover, POST /api/account/email
  defenses/                     login_throttle · population_signals · breached_passwords · oracles · risk_engine (your five
                                stubs) · ladder.py (yours) · ratelimit · breachcorpus (finished helpers)
  solutions/round1..4/defenses/ the finished checks and the ladder as it stands after each round
  attacks/                      round0_naive_stuffer · round1_distributed_stuffer · round2_clean_list_stuffer
                                round3_stealer_log_replay · round4_session_replay · _common.py
  tools/                        personas_ch6.py (the 132 people) · checkpoint.py (ROUNDS and thresholds)
```

The rest of the store (catalog, cart, checkout, the simulated edge, the decision log) is the W2 starter, unchanged. Its contract is `workshops/STORE_CONTRACT.md`.

**How a defense sees a login.** The starter checks a request *before* the route runs (`guard("login")`, phase `action:login`), which is the right moment for a rate limit but too early to know whether the password was right. `demo_site/ext/ato.py` adds a second phase, `action:login_result`, that runs after the route with the outcome in `ctx.attrs["login"]` (`ok`, `email`, `known`, the password tried). Counters update there, and so do the checks that only make sense once the password is right. A check that asks for a challenge takes the session back: the store emails a six-digit code to the account (read it in `/lab/mailbox/<email>`) and the session exists only after `POST /api/challenge/verify`. A failed login is never rewritten; it keeps its 401.

## Setup

Work through `PREWORK.md` first. This lab needs nothing beyond the starter's packages:

```bash
cd lab
python3.12 -m venv .venv && . .venv/bin/activate        # one venv per chapter, see the root README
pip install -r requirements.txt
python tools/doctor.py
python demo_site/app.py                                  # terminal 1: the store, on :5000 (seeds itself)
python tools/checkpoint.py --round 0                     # terminal 2: attackers and tools
```

Docker is optional: the default is SQLite plus an in-process Redis. To run the production-shaped stack (Redis 8.10 and PostgreSQL 18):

```bash
docker compose up -d --wait
REDIS_URL=redis://127.0.0.1:6379/0 DATABASE_URL=postgresql+psycopg://workshop:workshop@127.0.0.1:5432/shop python demo_site/app.py
docker compose down -v                                   # when you are done
```

Round N runs at `DEFENSE_LEVEL` N and each level includes every level below it; the checkpoint changes the level live (`POST /lab/level`), so the store never restarts between rounds. You finish a stub, wire it in `defenses/ladder.py`, save (the store reloads `defenses/` on the next request), and measure:

```bash
python tools/checkpoint.py --round 1                    # your code
python tools/checkpoint.py --round 1 --catch-up         # the reference solutions for rounds 1..1 (your files kept as .bak)
python tools/checkpoint.py --restore                    # put your own files back
python tools/checkpoint.py --round 1 --level 0          # the round's attackers against the PREVIOUS level (the "before")
```

| Level | Round | Adds | Module you finish |
|---|---|---|---|
| 0 | 0 | Nothing: logins are not throttled, screened or scored | – |
| 1 | 1 | Per-IP velocity and per-account lockout | `defenses/login_throttle.py` |
| 2 | 2 | Per-cohort (/24, /64) failure and unknown-account ratios | `defenses/population_signals.py` |
| 3 | 3 | A correct-but-breached password needs an emailed code; the recover oracle is closed | `defenses/breached_passwords.py`, `defenses/oracles.py` |
| 4 | 4 | Device and network context at login; a fresh proof for an email change | `defenses/risk_engine.py` |

Each check scores on the starter's 0 to 100 scale (`defenses/policy.py`): 40 and up is a `challenge` (the cohort challenge has no solver in this lab, so it is enforced as a block; the emailed code is the `otp` challenge), 75 and up a `block`. A rate limit is a hard `rate_limit` verdict.

Lab routes (loopback only, never scored): `/whoami`, `/lab/status`, `/lab/decisions`, `/lab/scoreboard`, and `/lab/mailbox/<email>` for the codes the store "emailed".

> Every response carries `X-Lab-Verdict`, `X-Lab-Score` and `X-Lab-Signals` (for example `rate_limit:ip_velocity`). That is for teaching only. In production, never tell a client which rule caught it.

## The people

`tools/personas_ch6.py` replaces the starter's 40 browsing shoppers with 132 people who sign in through `POST /api/login`, plus the 10 victims of Rounds 3 and 4. Every one is a seed user.

| Persona | n | Accounts | Who they are | Which round costs them |
|---|---|---|---|---|
| `returning` | 50 | 030 to 079 | strong password, usual device, own home address | nobody: they must never be stopped |
| `breached` | 12 | 018 to 029 | a top-30 password (also in the stuffers' lists) | Round 3: an emailed code |
| `typo` | 15 | 080 to 094 | one wrong password, then the right one | nobody: a wrong password is not a false positive |
| `cgnat` | 35 | 095 to 129 | 35 people behind **one** carrier-NAT address | Round 1: the IP limit refuses the 31st person onward |
| `new_device` | 20 | 130 to 149 | a home sign-in first, then a new phone on another network | Round 4: an emailed code |

**Hurt** means a person ended without a session. **Stepped up** means they were asked for a code and entered it: friction, not harm. The CGNAT cost appears in Round 1 and stays on every later scoreboard.

## Round 0: the baseline (`DEFENSE_LEVEL=0`)

| Step | Do | Expected |
|---|---|---|
| 🗡️ Attack | `python attacks/round0_naive_stuffer.py` | 30 accounts taken over (all of `user000` to `user029`) |
| ✅ Checkpoint | `python tools/checkpoint.py --round 0` | naive 28 to 30 · nobody hurt |

The combo list is 1000 pairs, 30 of them valid. One address, 16 workers, seconds. Everything below raises that cost.

## Round 1: 🔵 login throttling ⚔️ 🔴 distributed stuffer (`DEFENSE_LEVEL=1`)

| Step | Do | Expected |
|---|---|---|
| 🛡️ Defend | Finish `defenses/login_throttle.py` (per-IP sliding window, per-account lockout), wire `1: [login_throttle.CHECK]` in `defenses/ladder.py` | – |
| 🗡️ Re-run naive | `python attacks/round0_naive_stuffer.py` | throttled to 0 to 3 accounts |
| 🗡️ Attack | `python attacks/round1_distributed_stuffer.py` (one try per account, 60 rotating addresses) | 26 to 30 accounts again |
| ✅ Checkpoint | `python tools/checkpoint.py --round 1` | naive 0 to 3 · distributed 26 to 30 · **5 CGNAT people refused** |

**False-positive check:** 35 people share one address and the limit is 30 per minute. That is the cost of the cheapest defense; note it and carry it forward.

## Round 2: 🔵 population signals ⚔️ 🔴 clean-list stuffer (`DEFENSE_LEVEL=2`)

| Step | Do | Expected |
|---|---|---|
| 🛡️ Defend | Finish `defenses/population_signals.py` (per-cohort failure and unknown-account ratios), wire `2: [population_signals.CHECK]` | – |
| 🗡️ Re-run distributed | `python attacks/round1_distributed_stuffer.py` | cohort latched after 30 attempts: 0 to 3 accounts |
| 🗡️ Attack | `python attacks/round2_clean_list_stuffer.py` (prune through `/api/account/recover`, then 384 residential-proxy addresses) | 26 to 30 accounts (pruned 1000 to 30) |
| ✅ Checkpoint | `python tools/checkpoint.py --round 2` | distributed 0 to 3 · clean-list 26 to 30 |

**Discuss:** the clean-list stuffer confirms which addresses have accounts through the recover endpoint, then gives each attempt its own network. No cohort reaches the sample floor, so none can be challenged without challenging everyone.

## Round 3: 🔵 breached-password step-up + oracle hardening ⚔️ 🔴 stealer-log replay (`DEFENSE_LEVEL=3`)

| Step | Do | Expected |
|---|---|---|
| 🛡️ Defend | Finish `defenses/breached_passwords.py` and `defenses/oracles.py`, wire `3: [breached_passwords.CHECK, oracles.CHECK]` | – |
| 🗡️ Re-run clean-list | `python attacks/round2_clean_list_stuffer.py` | the oracle answers everyone alike (nothing pruned), every valid hit is breached: **0 accounts** |
| 🗡️ Attack | `python attacks/round3_stealer_log_replay.py` (10 victims' fresh, never-breached credentials and device cookie, from a datacenter) | 9 to 10 of 10 |
| ✅ Checkpoint | `python tools/checkpoint.py --round 3` | clean-list 0 · stealer 9 to 10 · **12 breached people stepped up** |

**False-positive check:** screening breached passwords is the best single control against stuffing, and the 12 real users whose password is genuinely in the corpus now enter a code. They get in; count it as friction.

## Round 4: 🔵 device and network risk + fresh proof ⚔️ 🔴 session-cookie replay (`DEFENSE_LEVEL=4`)

| Step | Do | Expected |
|---|---|---|
| 🛡️ Defend | Finish `defenses/risk_engine.py` (`CHECK` at login, `REAUTH` on an email change), wire `4: [risk_engine.CHECK, risk_engine.REAUTH]` | – |
| 🗡️ Re-run stealer | `python attacks/round3_stealer_log_replay.py` | a code goes to the victim's inbox: **0 accounts** |
| 🗡️ Attack | `python attacks/round4_session_replay.py` (replays 10 stolen `sid` + `did` cookies) | reads 10 of 10, **0 email changes** |
| ✅ Checkpoint | `python tools/checkpoint.py --round 4` | stealer 0 · reads at least 9, changes 0 · **32 people stepped up** (12 breached, 20 new device) |

**Debrief:** the stolen cookie still reads the account, because login-time defenses never see it. Re-auth stops the *damage* (the email change); stopping the read needs device-bound sessions (DBSC), passkeys or session-anomaly models. That is the hand-off to W2 Ch7 (ML) and W4.

## Wrap-up: false positives and cost

Pull the scoreboards together. The arc is the point: no single layer wins, and the cheapest layer (the per-IP limit) has the bluntest false-positive profile (CGNAT), while the sharpest (breached-password screen, device and network context) cost recoverable friction instead of hard blocks.

## Expected results (self-check)

Generated from `python tools/verify.py --all --catch-up --markdown` (against your own store: `python tools/checkpoint.py --all --markdown`) on 2026-10-14 on Linux x86_64 (WSL2) with Python 3.12.15, Flask 3.1.3, Flask-SQLAlchemy 3.1.1, SQLAlchemy 2.1.4, redis 8.1.0, fakeredis 2.39.0, requests 2.34.2, SQLite and the in-process Redis. Every round passed with the reference solutions installed, and every `--level N-1` "before" run reported the round's attacker getting through (all accounts or victims). The Docker path (Redis 8.10, PostgreSQL 18) was run for the smoke test and Rounds 1, 3 and 4: it passes. Small run-to-run variation (±1 account on the stuffers, depending on which valid pairs land before a limit trips) is normal. "Taken over" means a session obtained through the front door; Round 4's replay counts reads and email changes separately.

| Round | Level | Attackers run | Taken over (before → after) | CGNAT refused | Stepped up | Gate per sign-in, median / p95 |
|---|---|---|---|---|---|---|
| 0 | 0 | naive | 30 | 0 | 0 | 3.2 / 5.8 ms |
| 1 | 1 | naive, distributed | naive 30 → **0 to 3** (2 in the reference run) · distributed 30 → **29** | **5** of 35 | 0 | 4.9 / 8.7 ms |
| 2 | 2 | distributed, clean-list | distributed 30 → **1** · clean-list 30 → **30** (pruned 1000 to 30) | 5 | 0 | 6.2 / 8.6 ms |
| 3 | 3 | clean-list, stealer | clean-list 30 → **0** · stealer 10 → **10** | 5 | **12** (breached) | 5.5 / 10.4 ms |
| 4 | 4 | stealer, replay | stealer 10 → **0** · replay reads 10 → **10**, email changes 10 → **0** | 5 | **32** (12 breached, 20 new device) | 7.1 / 9.7 ms |

Typos: all 15 are rejected once with a 401 at every level and then sign in; that is correct behavior, not a false positive. The gate figure is the median over the people's sign-ins while the attackers hammer the same store (Ctx build, enrichers and every check, from the decision log; not the PBKDF2 hash). With the Docker stack it is much higher under the same load (about 100 ms median in Round 3, about 70 ms in Round 1) because each sign-in makes about ten Redis round trips; the checkpoint allows 250 ms there instead of 20 ms. Write the counters as one Lua script or pipeline before you ship them.

## Troubleshooting

| Problem | Fix |
|---|---|
| Port 5000 taken (macOS AirPlay Receiver) | `PORT=5050 python demo_site/app.py`, then `export DEMO_URL=http://127.0.0.1:5050` in the shells that run tools |
| Round 1 fails with `naive: 30 accounts taken over` | Your stub is not finished, or not wired in `defenses/ladder.py`. Finish the `TODO`, or `python tools/checkpoint.py --round 1 --catch-up` |
| Every login from your browser is refused | You are the CGNAT cohort: your address is `student_ip`. `POST /lab/reset` clears the counters |
| A round says `store is at level N` | The checkpoint sets the level itself; if you changed it by hand, run the checkpoint again |
| Numbers look stale between rounds | The checkpoint resets the store (`POST /lab/reset`); if you ran an attack by hand, run the checkpoint to reset first |
| `ModuleNotFoundError: demo_site` | Run scripts from `lab/` (`python attacks/...`), not from inside `attacks/` |
| Want a clean slate | Stop the store, delete `instance/`, start it again |
| Port 5432 or 6379 taken (another lab's containers) | `docker compose ls`, then `docker compose -p <name> down` |
