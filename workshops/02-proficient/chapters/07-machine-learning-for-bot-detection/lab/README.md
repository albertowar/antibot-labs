**Format:** Round 0 plus 4 rounds of defend 🛡️ and attack 🗡️, then a debrief. See `workshops/02-proficient/chapters/07-machine-learning-for-bot-detection/chapter_07_content.md` (slides repo), §7.6. **Style: wire-it.** Four modules ship as stubs with a `TODO (Round N)`; the finished versions are in `solutions/roundN/`. `--catch-up` installs rounds 1..N (and **trains the reference models**), and `--restore` puts your files back. Everything around the stubs (features, labels, training, the explainer, the simulators) is finished code you read and run.

It is drop day at Kestrel Outfitters: the Kestrel One Hoodie (`lab-hoodie-1`) goes live. You play both sides. As the **defender** you train a model on the store's own event log and switch it on at the purchase. As the **attacker** you run the bot that beats it. Every round ends with a checkpoint that reports bots stopped *and* real customers blocked.

## Rules of engagement

- **Local only, enforced in code.** Every attack script and tool imports `tools/labclient.py`, which asks `labnet.py` at the lab root for `DEMO_URL` and refuses anything that is not this machine (side-service URLs such as `REDIS_URL` too). Do not remove that check.
- **Everything is synthetic.** The 600 + 200 customers and the bots are generated by `tools/personas_ch7.py` and `attacks/`; the accounts are the starter's seed users `user000..299@example.test`. Source addresses are rented from `data/world.json` (documentation ranges) and sent in `X-Lab-Client-IP`, which the store's edge trusts only from loopback. Residential proxies, VPNs and carriers are *simulated*; the proxy and fingerprint prices are made up. The "browser" is Python: the fingerprints and behaviour summaries it posts stand in for the W2 Ch5 and W2 Ch2 collectors.
- **Outbound network:** none during the rounds. The model trains offline on the synthetic history in `data/history/`. Only setup needs the internet: installing packages and container images.
- The simulator's answer key (who was really a bot) is `data/history/truth.jsonl`, written from the decision log. Only `tools/audit.py` reads it. **Never train on it**: production has no such file.
- Do not point these scripts, or anything you build from them, at a site you do not own.

The rest of the store (catalog, cart, checkout, the simulated edge, the decision log, the scoreboard) is the W2 starter. Its contract is `workshops/STORE_CONTRACT.md`.

**Why Python only.** Everything in this chapter is server-side: feature extraction from logs, model training and inline scoring, and the data and ML stack (pandas, scikit-learn, LightGBM) is the standard tool for it. The browser-side collectors that produce the telemetry were built in W2 Ch5 and W2 Ch2; here the simulated customers post the same summaries straight to `POST /api/telemetry`, so no browser is needed.

**Where the data lives.** The store appends one event per request (assets included, they are the cheapest tell of a script) to its Redis, and `POST /lab/reset` wipes it with the rest of the lab state. The *training set* is a file: `tools/simulate.py` generates the drop day and appends the store's log to `data/history/`; `tools/label_cluster.py` and `tools/explain.py` pull whatever attack traffic you sent since. Training reads that history and nothing else. Online, `ml_check.py` reads the live session and its cohort from Redis and calls the **same** `features.compute()`.

Docker is optional: the default is SQLite plus an in-process Redis. To run the production-shaped stack (Redis 8.10 and PostgreSQL 18):

```bash

docker compose down -v                                   # when you are done
```

Round N runs at `DEFENSE_LEVEL` N and each level includes every level below it; the checkpoint changes the level live (`POST /lab/level`), so the store never restarts between rounds. Models hot-reload when their files change.

```bash
python tools/checkpoint.py --round 1                    # your code
python tools/checkpoint.py --round 1 --catch-up         # the reference solutions for rounds 1..1, and the reference models (your files kept as .bak)
python tools/checkpoint.py --restore                    # put your own files back
python tools/checkpoint.py --round 1 --level 0          # the round's attackers against the PREVIOUS level (the "before")
```

| Level | Round | At the purchase (`POST /drop/lab-hoodie-1`) | You finish | Needs |
|---|---|---|---|---|
| 0 | 0 | log only, every order confirmed | nothing | the event log |
| 1 | 1 | model v1: per-session features | `ml_check.py`, `ladder.py` | `artifacts/model_v1.*` |
| 2 | 2 | model v2: + cohort features and analyst labels | `cohort.py` | `artifacts/model_v2.*` |
| 3 | 3 | v2 + the anomaly detector, `risk = max(p/t, a/t_a)` | `anomaly.py` | + `artifacts/anomaly_v3.json` |
| 4 | 4 | level 3 scoring, deferred enforcement: 202 for everyone, cancel at review | `enforcement.py` | as level 3 |

The model scores on the starter's 0 to 100 scale: **75 points per unit of risk** up to the blocking line, then a smooth climb towards 100 (`points()` in `ml_check.py`). Risk 1.0 is `policy.BANDS["block"]`, a purchase is blocked at `risk >= 1.0`, and at levels 1 to 3 the gate's `X-Lab-Score` header rises with the risk on both sides of the line. That is a **teaching aid, and a deliberate mistake**: Round 3 exploits it and Round 4 removes the oracle. In production you would run with `LAB_HEADERS=0`, and the 200-or-403 answer alone is still an oracle.

**Lab time.** Simulated customers think for seconds between pages. `LAB_TIME_SCALE=0.02` (the default) sleeps 2% of that, so a drop day of 900 sessions takes about 2 minutes — but each request carries the session's *virtual* clock (`X-Virtual-Ts`, advanced by the full think time), and that is what the store records and the features read. So the recorded timeline, the trained model and the expected-results table are the same on any machine and under any load: `LAB_TIME_SCALE` only shortens the sleeps, never the feature values.

**Stock.** A drop day sells thousands of units. The checkpoint resets the store with 20000; a store you start by hand lifts the drop to 5000 at start (set `DROP_STOCK` to choose).

| Step | Do | Expected |
|---|---|---|
| 🛡️ Generate | `python tools/simulate.py` (the store at any level; it sets level 0 while it runs) | 900 sessions, every order confirmed; the history appears in `data/history/` |

| ✅ Checkpoint | `python tools/checkpoint.py --round 0` | baseline bots 100% succeed · 0 real customers blocked |

**Discuss:** which bots carry a label, and which humans? What will a model trained on these labels learn "bot" means?

*Model answer:* the labels are precise and biased. The bot labels come from honeypot hits, so the model learns what bots that follow hidden links look like; the human labels come from signed-in, long-standing customers, so it barely meets VPN, privacy-browser and new users. Everything it learns is relative to those two groups.

## Round 1: 🔵 model v1 ⚔️ 🔴 the humanized bot (`DEFENSE_LEVEL=1`)

| Step | Do | Expected |
|---|---|---|
| 🛡️ Defend | Finish `_check()` in `defenses/ml_check.py` and wire `1: [ml_check.CHECK]` in `defenses/ladder.py`; train with `python -m defenses.train --round 1` | holdout AUC 1.000 for both models; the 1% budget cannot place the line (every verified human scores about 0), so the 0.5 floor is used. Top features: `first_input_s`, `scrolls`, `software_gpu` |
| 🛡️ Exercise | `python -m defenses.train --round 1 --include-leaky` (never saves a model) | AUC still 1.000, and `honeypot_hits` (the label definition) enters the top features |
| 🛡️ Exercise | `EXERCISE (Round 1)` in `defenses/train.py`: `--fpr-budget 0.002`, then `0.05` | 0.002 moves the line to about 0.999 (one verified customer scores high out of fold, and a 121-person sample cannot resolve 0.2%); 0.05 falls back to the floor |
| 🗡️ Re-run baseline | switch to level 1 (`curl -s -X POST localhost:5000/lab/level -H 'content-type: application/json' -d '{"level": 1}'`), then `python attacks/round0_baseline.py` | 0 of 60 purchases |
| 🗡️ Attack | read `attacks/round1_humanized.py`, then run it | 60 of 60 succeed; `X-Lab-Score` 0 on every purchase: the model is certain these are customers |
| ✅ Checkpoint | `python tools/checkpoint.py --round 1` | baseline 0 to 10% · humanized 90 to 100% · real customers at most 6 of 200 |

**False-positive check:** the cohort table. v1 leans on `first_input_s` almost alone: the headless bots click within 120 ms and no loyal customer ever does, so a *fast* customer pays. In the reference run it is one `power_user` whose first input came after 0.2 s (score 87, blocked). Which cohort pays depends on which sessions happen to carry a human label; in other runs it has been a keyboard-only user. Find the blocked customer's `sid` in `GET /lab/decisions?path=/drop/lab-hoodie-1` and run `python tools/explain.py --model 1 --sid <sid>`.

**Discuss:** the validation AUC was 1.000 and the model still lets every humanized bot through. What did the AUC measure?

*Model answer:* it measured how well the model separates the two groups that carry labels: honeypot-hitting bots and loyal customers. Nothing resembling the humanized bot was ever labeled, so the AUC says nothing about it. A perfect AUC on weak labels is a bug report, not a result.

## Round 2: 🔵 cohort features ⚔️ 🔴 the fingerprint farm (`DEFENSE_LEVEL=2`)

| Step | Do | Expected |
|---|---|---|
| 🔍 Triage | `python tools/explain.py --model 1 --allowed 4` | every contribution says "human"; the `fp` column repeats |
| 🛡️ Label | `python tools/label_cluster.py`, answer `y` | six clusters are labeled: the stealth profile (one fingerprint over about 44 addresses) and the headless fleet's container images. The phone clusters, which sit on the two carrier addresses and contain verified customers, are not |
| 🛡️ Defend | Finish `features()` in `defenses/cohort.py`; `python -m defenses.train --round 2`, then add `--random-split` | the temporal holdout collapses for LightGBM (AUC 0.5 to 0.9 depending on the run; the logistic baseline holds up better); the random split hides it (1.000); the top features become `fp_ip_fanout_1h` and `fp_sessions_1h` |
| 🛡️ Exercise | `EXERCISE (Round 2)` in `cohort.py`: add a cohort feature of your own, retrain | – |
| 🗡️ Re-run humanized | switch to level 2, `python attacks/round1_humanized.py` | 0 of 60 get through; `explain.py --model 2 --sid <sid>` shows `fp_ip_fanout_1h` doing the work |
| 🗡️ Attack | `python attacks/round2_farm.py` | all succeed: every cohort count is 1 |
| ✅ Checkpoint | `python tools/checkpoint.py --round 2` | humanized 0 to 20% · farm 60 to 100% · real customers at most 10 of 200 (5%; Round 1 allowed 6. Cohort features hurt the customers who share a fingerprint or an address with a bot wave, and how many depends on timing, so a run lands between 6 and 10) |

`label_cluster.py` first pulls the store's live log (the humanized wave you just sent) into `data/history/`; that is how the history grows. `explain.py` and `audit.py` do the same.

**False-positive check:** the stealth profile is "a common Windows + NVIDIA + Chrome desktop", and a few real customers own exactly that device. The cluster of about 60 sessions the tool labels contains three of them (no verified human among them to veto it), so v2 blocks real customers with that device: `desktop` 1 to 3 of 96 on every scoreboard from here on. Run `python tools/explain.py --model 2 --sid <sid>` on one: `fp_ip_fanout_1h = 41` pushes it to "bot". Same fingerprint, different people.

**Discuss:** the burst is caught because its sessions overlap in time. How would you change `round1_humanized.py` to stay under every cohort count, and what would that cost the attacker on a drop that sells out in minutes?

*Model answer:* spread the sessions out (one every few minutes, or one address per session over a long window) so no window holds more than one or two of them. That costs time, and a drop that sells out in minutes ends before the campaign has bought anything; on an always-on target the delay costs nothing, which is the limit of population features.

*Model answer:* every datacenter bot in the labels also behaved like a script, so behaviour explained the label and `asn_type` added nothing. Correlated features in the labels become blind spots in the model; a rule layer (Chapter 8) covers what the labels never separated.

## Round 4: 🔵 deny the oracle (`DEFENSE_LEVEL=4`)

| Step | Do | Expected |
|---|---|---|
| 🛡️ Defend | Finish `decide_later()` and `state()` in `defenses/enforcement.py`, switch to level 4 | every purchase: 202 `pending`, `X-Lab-Score` 0 |
| 🗡️ Re-run | `python attacks/round3_oracle_prober.py` | every probe looks identical; it buys the cheapest configuration; the exploit is cancelled at review (0 of 30) |
| 🗡️ Patient | `python attacks/round3_oracle_prober.py --patient` | tries all 16 configurations (32 probes), waits one review, and the exploit works again (30 of 30) |
| 🛡️ Exercise | `EXERCISE (Round 4)` in `enforcement.py`: `REVIEW_DELAY_S` | a longer review: a slower prober, longer-held inventory |
| ✅ Checkpoint | `python tools/checkpoint.py --round 4` | prober 0 to 10% · patient 60 to 100% · real customers at most 10 of 200 (cancelled count as hurt) |

The starter's scoreboard counts a customer as hurt when the *last thing the gate did* was a stop. At level 4 the gate stops nobody, so its "shoppers hurt" is 0; the cancellations happen later, at review. The checkpoint's **real customers** table counts them, and that table is the one to read.

**Discuss:** the patient prober won. What did deferred enforcement buy you, and what did it cost real customers?

*Model answer:* it removed the per-probe gradient, so a prober needs one review cycle and every configuration paid for up front (32 probes, about eight dollars) instead of six cheap probes. It cost inventory held by bots until review and a few customers cancelled by email after the fact, which is worse than a challenge at the time.

## Expected results (self-check)

Generated from `python tools/verify.py --all --catch-up --markdown` (against your own store: `python tools/checkpoint.py --all --markdown`) on 2026-10-18 on Linux x86_64 (WSL2) with Python 3.12, Flask 3.1, redis 8.1, fakeredis 2.39, LightGBM 4.7 and the in-process Redis. Every round passed with the reference solutions installed, and every `--level N-1` "before" run reported the round's attacker getting through. The trained model is now reproducible — features read the session's virtual clock, not measured wall gaps, so a history regenerated on any machine trains a byte-identical model (verified: two clean regenerations, identical `model_v1.txt`). Customers are 200 people in six cohorts. "Hurt" is a customer blocked at the purchase or, at level 4, cancelled at review. The customers still shop on 16 threads, so which of them lands next to a bot wave inside a cohort window varies by a few between runs (Round 2 landed on 7, 8 and 9 across runs, Round 4 on 6 to 8) — the model is stable, this residual jitter is the online cohort window, which is why the budget from Round 2 on is 10 of 200 (5%). The Docker path (Redis 8.10, PostgreSQL 18) was run for the smoke test and Round 3: it passes (7 of 200 hurt; the model check is slower there, median 33 ms, because the features read Redis over the network).

| Round | Level | Attackers run | Succeeded (before → after) | Customers hurt | Model check per purchase, median / p95 |
|---|---|---|---|---|---|
| 0 | 0 | baseline | baseline 40 of 40 | 0 | not scored |
| 1 | 1 | baseline, humanized | baseline 40 → **0** · humanized 30 of 30 | 1 (a power user) | 3.7 / 11.5 ms |
| 2 | 2 | baseline, humanized, farm | humanized 30 → **0** · farm 30 of 30 | 8 (5 desktop, 2 power users, 1 VPN) | 4.4 / 11.5 ms |
| 3 | 3 | + prober | farm 30 → **0** · prober 30 of 30 (6 probes) | 6 | 5.2 / 12.6 ms |
| 4 | 4 | farm, prober, patient | prober 30 → **0** · patient prober 30 of 30 (32 probes, about $8 of probing) | 7, all cancelled at review | 5.6 / 123 ms |

Round 0's hurt count is zero because nothing is scored; the weak labels cover part of the bots and are never wrong (the checkpoint audits both). The five desktop customers hurt from Round 2 on are mostly people who own exactly the stealth bot's device or sit next to the bot wave in the same cohort window, which is the false positive the chapter warns about. At level 4 the scoreboard's own "shoppers hurt" is 0 (the gate stops nobody); read the checkpoint's customer table instead. The p95 of the model check at level 4 reflects 16 threads contending for a single CPU; the median is the figure to compare.

## Bonus challenges

1. **Hindsight review.** At level 4, recompute cohort features at *review* time, with a window that includes sessions after the purchase. How much of the prober's exploit wave does that catch, and why can't you do it inline?
2. **Smarter prober.** Make `round3_oracle_prober.py` ignore `X-Lab-Score` and use only the status code at level 3. How many more probes does it need?
3. **Positive-unlabeled learning.** Train on "labeled bot vs. everything else" instead of "labeled bot vs. verified human". What happens to false positives on VPN users?
4. **Calibration.** Wrap the model in scikit-learn's `CalibratedClassifierCV`, or compare it with `TunedThresholdClassifierCV` using a cost metric: 1 blocked customer costs as much as 20 missed bots.
